# css-performance-budgeting

## Purpose
Control CSS runtime/rendering risk with explicit budgets, diagnostics, and release gates.

## When to Use
- Performance regressions after styling changes.
- Large refactors affecting selectors, themes, layout primitives, or animation.
- Launch readiness for landing pages and component libraries.

## Required Inputs
- Baseline metrics (LCP/INP/CLS + style recalculation and paint timings).
- Browser/device matrix (Chrome, Safari, Firefox; mid-tier mobile + desktop).
- CSS architecture map (framework mix, token layers, critical CSS path).
- Target budgets per template/page family.

## Budget Categories
1. **Payload and unused CSS**: gzip/brotli budget, dead-rule threshold, per-route CSS limits.
2. **Selector/cascade complexity**: max nesting depth, disallow deep descendant chains, cap layered overrides.
3. **Layout/reflow risk**: budget forced sync layout events, avoid layout-thrashing properties.
4. **Paint/composite cost**: identify expensive effects (blur, large shadows, filters) and hotspot screens.
5. **Animation frame budget**: keep interaction animations inside 16.7ms frame budget; prefer transform/opacity.
6. **Critical CSS/render blocking**: route-critical styles inline/early, defer non-critical bundles.
7. **Responsive/theme cost**: budget additional selectors generated by breakpoints, themes, and variants.

## Browser Diagnostics Workflow
1. Reproduce in Chrome Performance panel with CPU slowdown.
2. Capture style recalculation, layout, paint, and long-task events.
3. Validate in Safari Web Inspector + Firefox Profiler for engine-specific behavior.
4. Compare before/after traces; annotate CSS changes tied to regressions.
5. Document accepted deltas and rollback triggers.

## Review Checklist
- Are new selectors compatible with existing cascade layers?
- Did rule count or specificity increase beyond budget?
- Any animation touches layout-triggering properties?
- Did critical CSS grow and block first paint?
- Are reduced-motion and low-end device checks included?

## Regression Policy
- **Acceptable**: <=3% payload increase with measurable UX benefit and no timing regressions.
- **Warning**: 3-8% growth or minor timing drift; requires follow-up ticket and owner.
- **Blocking**: >8% payload growth, increased jank, or cross-browser layout/paint regressions.

## Integrations
- With `animation-motion`: enforce motion frame budgets and reduced-motion behavior.
- With `layout-responsive`: detect breakpoint-driven reflow spikes.
- With `site-wide-systems`: apply budgets across page families and themes.
- With `css-review-audit`: severity mapping and remediation backlog.
- With `frontend-dev-guidelines`: add PR gates and CI checks for style payload/perf evidence.

## Failure Modes and Rejection Criteria
Reject changes when:
- Performance claims lack baseline/after measurement.
- Specificity/cascade complexity rises without architecture rationale.
- Reflow-heavy patterns introduced without alternatives.
- Theme/responsive variants duplicate large rule sets without consolidation plan.
